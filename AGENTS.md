# AGENTS.md — Правила разработки для AI-агентов (PeerCheck)

Этот файл задаёт контекст, ограничения и архитектурные правила для AI-ассистентов (Copilot, ChatGPT, Cursor, Claude и др.), которые работают с кодом проекта **PeerCheck**.

---

## 1. Контекст проекта и команды

* **Продукт:** веб-сервис анонимного взаимного рецензирования студенческих лабораторных работ (P2P-ревью). Студент регистрируется по почте и паролю, система выдаёт ему случайный псевдоним, и другие пользователи видят только этот псевдоним.
* **Команда:** студенты 1-го курса под руководством наставника.
* **Специфика:** студенты только осваивают Python и Git. Они должны **понимать каждую строчку кода**, уметь объяснить его на созвоне и защитить перед преподавателем. Если студент просит написать код, объясни, что делает каждая часть. Не добавляй ничего сверх того, что требует задача.
* **Главный принцип:** **KISS (Keep It Simple, Stupid)**. Простота и читаемость важнее «продвинутых» абстракций.

## 2. Технологический стек и ограничения

| Компонент | Разрешено | Запрещено |
| :--- | :--- | :--- |
| **Язык** | Python 3.10+, синхронный код | `async/await`, `asyncio`, метаклассы, сложные замыкания |
| **Интерфейс** | `streamlit` (стандартные виджеты, `st.session_state`, `st.navigation`, `st.pdf`) | Внешние JS-фреймворки, самописный CSS/HTML, iframe |
| **База данных** | Встроенный модуль `sqlite3`, файл `peercheck.db` | ORM (`SQLAlchemy`, `Peewee` и др.), сложные SQL-процедуры |
| **Файлы** | `pathlib.Path`, `os`, `shutil`, `uuid`, каталог `uploads/` | Облачные хранилища (S3, MinIO) |
| **Учётные записи** | `hashlib.pbkdf2_hmac`, `hmac`, `os.urandom` из стандартной библиотеки | `bcrypt`, `passlib`, OAuth, внешние сервисы входа, хранение пароля в открытом виде |
| **Зависимости** | Только то, что в `requirements.txt` (`streamlit[pdf]`: Streamlit и просмотр PDF через `st.pdf`) | Новые пакеты без согласования с наставником |

## 3. Архитектура

Код разделён на **2 модуля в корне** (база и логика) и **экраны интерфейса**, каждый экран в своём файле. У каждого файла свой ответственный, поэтому два человека не правят один файл:

```text
peer-check/
├── app.py                # [наставник] Точка входа: настройка страницы, меню (st.navigation), кнопка «Выйти»
├── screens/              # Экраны Streamlit, по одному файлу на экран
│   ├── home.py           # [Виталина] «Как это работает»
│   ├── login.py          # [Егор] «Вход и регистрация»
│   ├── submit.py         # [Виталина] «Сдать лабораторную»
│   ├── review.py         # [Егор] «Проверить чужую работу»
│   └── my_reviews.py     # [Кирилл] «Мои отзывы»
├── database.py           # [Кирилл] Работа с SQLite: работы, рецензии, учётные записи
├── roulette.py           # [Егор] Логика: рулетка, проверка отзыва, доступ к отзывам,
│                         #        псевдонимы, пароли, сохранение PDF
├── test_roulette.py      # Автотесты для roulette.py
├── seed_demo_data.py     # [Кирилл] Демо-пользователи, работы и рецензии для показа
├── requirements.txt
├── AGENTS.md             # Этот файл
├── peercheck.db          # Локальная БД (в .gitignore, не коммитится)
├── uploads/              # Загруженные PDF (в .gitignore, не коммитится)
└── docs/                 # Документация для команды
    └── architecture_contracts.md  # Схема БД и сигнатуры функций
```

### Правило контрактов
* **Не придумывай новые имена функций!** Все вызовы между экранами, `database.py` и `roulette.py` зафиксированы в [docs/architecture_contracts.md](docs/architecture_contracts.md).
* Экран меняй только в своём файле в `screens/`. Новые экраны и пункты меню добавляет наставник в `app.py`.
* У каждой функции в контрактах есть статус: **[есть]**, **[есть, исправить]**, **[задача #N]** или **[запланировано]**. Функцию со статусом **[запланировано]** не пиши, пока её нет в задаче студента.
* Если нужна новая функция, сначала договорись с наставником и добавь её контракт в этот файл.
* Сигнатуры `select_lab_for_review`, `validate_review`, `generate_pseudonym` и `calculate_final_score` дополнительно проверяет `test_roulette.py`. Не меняй их.

### Git
* Пока работаем напрямую в ветке `main` (Commit ➔ Push), без фиче-веток.
* Коммить только файлы своей задачи. Не коммить `.venv/`, `.idea/`, `*.db`, `uploads/`.

## 4. Стиль кода

1. **Docstring и комментарии:**
   * У каждой публичной функции краткий docstring на русском: что делает, какие аргументы, что возвращает.
   * Неочевидные шаги внутри функции комментируй простыми словами.
2. **Аннотации типов** пиши встроенными типами (Python 3.10+), без `typing.List/Optional`:
   `def add_submission(student_token: str, lab_number: int, file_path: str) -> int:`
   `def select_lab_for_review(current_user_token: str, available_labs: list[dict]) -> dict | None:`
3. **Ошибки:**
   * Функции в `database.py` и `roulette.py` возвращают предсказуемые значения: кортеж `(bool, str)`, `None` или `[]`.
   * В `app.py` перехватывай ошибки и показывай понятные сообщения через `st.error(...)` / `st.warning(...)`, а не трейсбек.

## 5. Анонимность и личные данные

* Пользователя везде определяет **псевдоним** из `st.session_state["pseudonym"]`. Именно он передаётся в функции как `student_token`, `reviewer_token` и `current_user_token`.
* **Пароль** никогда не хранится и не выводится в открытом виде: ни в базе, ни в `print`, ни на экране. В базу пишется только результат `hash_password`, проверка входа — только через `check_password`.
* **Почта** нужна только для входа. Не показывай её другим пользователям и не передавай в функции рулетки и отзывов.
* Не добавляй поле, где студент сам придумывает себе ник: псевдоним выдаёт система при регистрации.
* PDF сохраняется под именем, которое придумывает система. Исходное имя файла не сохраняй и не показывай: в нём бывает фамилия автора.

## 6. Фокус по модулям

* **`app.py` и `screens/`:** чистый интерфейс. `app.py` только настраивает страницу и меню. Каждый экран в `screens/` начинается с проверки входа (`if "pseudonym" not in st.session_state: ... st.stop()`) и берёт псевдоним из `st.session_state["pseudonym"]`. Сплит-экран проверки `st.columns([3, 2])`, PDF показывается через `st.pdf(...)`. Обязательные поля формы проверяй, каждую ошибку показывай отдельным `st.warning`. Выданную рулеткой работу храни в `st.session_state`, иначе при каждом действии пользователя Streamlit перезапускает страницу и рулетка выдаёт новую работу.
* **`database.py`:** параметризованные SQL-запросы с `?` (защита от SQL-инъекций), обязательный `conn.commit()` и `conn.close()`. Строки отдавай словарями: `[dict(row) for row in rows]`. Почту перед записью и поиском приводи к `email.strip().lower()`.
* **`roulette.py`:** логика без обращения к базе: функции получают данные аргументами и возвращают результат. Исключение — `save_uploaded_pdf`, она пишет файл в `uploads/`. Исключение своей работы из рулетки, валидация отзыва (`len(comment.strip()) >= 50`), правило доступа к отзывам, псевдонимы и хеширование паролей.
